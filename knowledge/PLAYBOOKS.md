# PLAYBOOKS — step lists for the recurring jobs of an agent-built monorepo

> Companion to `LESSONS.md`: the same lessons as procedures. Commands assume the workspace generated by SYSTEM_SETUP (`scripts/tasks.py`, `.claude/hooks`, `INTEGRATION.md` board, project masters from `.claude/projects.json`). `<master>` = the project's master branch, `<prefix>` = its task prefix, `<key>` = a short kebab-case key. Replace tool names (Gradle, Xcode, npm, Playwright) with the stack's equivalents.

## 1. Start a task
1. `cd <project folder>` (one project per session; only its `CLAUDE.md`/session/memory load). `git status` must be clean and on `<master>`.
2. `python3 scripts/tasks.py next <project>` → ID, title, branch, needs, notes. If it prints no ready task: `tasks.py blocked` and report the PENDING/BLOCKED rows; stop.
3. `git fetch origin && git branch --no-track <branch> origin/<master> && git checkout <branch>`; `git branch --show-current` must print the task branch before any edit.
4. `python3 scripts/tasks.py set <ID> "IN PROGRESS"` (it also rewrites the board; those file changes travel with the task).
5. Read only what the row names: `grep -n "^### S07" docs/<PRD>.md` → `sed -n '<start>,<end>p'`; the operation ids in the generated OpenAPI; `BUSINESS_DOMAIN.md` sections by heading. Two projects touched → `INTEGRATION.md` §1–§6 once.
6. Write the task block in the project's `.claude/session.md` (template in `.claude/hooks.md` §3) with acceptance criteria naming PRD §, BUSINESS_DOMAIN § and operation ids; `Loops: 0/1`, `Review: PENDING`. Keep current + last 2 blocks only.
7. Inspect the existing implementation, callers and tests (symbol search first, ranges only). Distinguish requirement from assumption; ask only when the repo cannot answer and it changes correctness.
8. Implement + unit tests; commit on the task branch after each coherent step (small commits survive dropped sessions).

## 2. Ship a task (single-task cadence)
1. Run the project's quiet gate (its `CLAUDE.md` §1 names it); read the summary only; fix until green. UI project: browser/simulator check of the changed screens in every language, light/dark, phone/tablet(/desktop), measured not inferred, console clean.
2. One verification loop: re-check every acceptance criterion (coverage, edge cases/errors/security/no-hardcode, tests/build/lint green, PRD/BRD consistency). Record `Loops: 1/1`.
3. Four-role review of `git diff origin/<master>...HEAD` (+ uncommitted): SE, Mobile (or N/A), Architect, QA; fix blocking findings, re-run tests. Record `Review: PASSED (…) — <summary>`.
4. Memory: one line per durable fact in the project's `.claude/memory.md` (replace, do not append); root `session.md` index line if the project's current task changed; contract change → affected client tasks named in the block.
5. Commit (code, tests, session/memory, backlog + board changes). Push from the Terminal panel if the sandbox blocks it — the `Loops`/`Review` lines must already be committed (the guard reads them first).
6. `tasks.py set <ID> "IN REVIEW"`, open the PR into `<master>` (never `main`), state in the body what was opened in the browser/simulator and every deviation.
7. Merge (merge commit) when the gate is green and the owner granted self-merge; `git checkout <master> && git pull`; `tasks.py set <ID> DONE` (unblocks dependents, rewrites the board) and commit that on the next task's branch or a `docs/` branch.
8. Final answer: what shipped, test results, deviations, owner inputs as one numbered list.

## 3. Batch-verify five (batched cadence, rules §3.13)
1. Per task: implement + unit tests, run the in-sandbox static checks (policy scripts, lint if cheap), task block with `Loops: 0/1` / `Review: PENDING`, commit, **branch the next task from this branch** (`git branch --no-track <next> HEAD`).
2. After the fifth task (or the backlog's end): one host unit-test run for the whole batch (one Gradle/npm invocation, nothing else running on the machine). Fix failures on the current branch.
3. Code reading of the batch diff per role → `Loops: 1/1` + `Review: PASSED` in all five blocks; UI check explicitly deferred in the Notes.
4. One PR from the last branch into `<master>`; merge; `tasks.py set <ID> DONE` for the five; board regenerated; memory one line per task.
5. After the whole backlog: linters/static analysis, the full gate (every variant and configuration), then one end-to-end journey on emulator + simulator (or browser), fixing findings in a final batch (playbook 6).

## 4. Sync masters ↔ main (with board conflicts)
1. `git fetch origin`; for each master: `git rev-list --left-right --count origin/main...origin/<master>` → behind/ahead.
2. Masters behind `main` first: `git branch --no-track chore/sync-main-into-<master>-N origin/<master> && git checkout` it, `git merge origin/main`.
3. Conflicts are almost always: `INTEGRATION.md` board (take either side, then `python3 scripts/tasks.py board` regenerates it), backlog rows (keep both rows, fix duplicates), root `.claude/session.md` blocks (keep all blocks). Product code conflicts mean two agents touched one project — stop and reconcile with the owner.
4. `grep -rn "<<<<<<<\|>>>>>>>" --include=*.md .` must be empty; `python3 scripts/tasks.py check` OK (known notes only); hook tests green if hooks changed.
5. Task block in root `session.md` (`<PREFIX>-NNN — Sync main into <master>`; `Loops: 1/1`, `Review: PASSED — merge only, no product code`). Commit, push, PR into `<master>`, merge.
6. Then masters → `main`: one branch from `main` merging each master (or one integration branch merging all when several conflict), same conflict rule, PR into `main` (owner merges, or you if granted).
7. Finally `main` → every master again so all are 0 behind; `git pull` each local master. Report ahead/behind counts measured, not assumed.
8. Never sync into an auto-deploying branch before the environment has the new env keys (merge into masters meanwhile).

## 5. Local QA stack
1. Terminal panel (not the sandbox: port binding is blocked): database, cache, object-storage emulator (docker compose from the server folder), then the server with `*_PROVIDER=fake`, the fixed one-time code and `.env.dev` placeholders; `env:check` first.
2. Seed with the server's one-command dev seed (idempotent; prints the test accounts' identifiers, never secrets).
3. Admin: `VITE_DATA_SOURCE=remote` + local API URL, served from your worktree on its own port. Apps: Android `10.0.2.2:<port>` with an untracked debug manifest (cleartext) and `adb reverse` for storage; iOS `Local.xcconfig` (git-ignored) with an ATS-allowed IP.
4. Smoke before any journey: `/health` vs `/ready`, one request through the newest endpoint (404 = stale build), seed counts.
5. Leave the stack running for other agents; never stop shared daemons you did not start. Stop your own processes and close the tabs when done.

## 6. End-to-end pass and collecting server defects
1. Fresh release-like build (dev flavour, minified if the gate allows), installed clean (`pm clear` / delete app), build newer than your last edit.
2. Walk the journey list from the PRD flows (`F01…`): every screen in each language/direction, light/dark, portrait/landscape, phone/tablet, large font; each data-bound element in loading/empty/error/success.
3. Per screen capture: screenshot + top activity/view controller + logs (`FATAL EXCEPTION|Caused by`, crash reporter console), measured widths/offsets for anything that looks off; a11y script for unlabeled clickables and targets < 48 dp.
4. Triage each finding: tooling artifact (clock skew, dropped adb keys, low RAM, stale install, hidden browser pane) → re-check; client defect → fix in the client task; server/contract defect (wrong shape, missing field, 5xx, stale deploy) → new server backlog row with reproduction + expected contract, client row BLOCKED on it.
5. Record in the final batch block: journeys run, device/simulator names, what was not covered, defects by project with ids.

## 7. Device integrations checklist (Android / iOS)
- **Owner inputs first (PENDING rows):** push project per environment, one registration per app × platform (Android package + SHA-1/256; iOS bundle id + APNs key), client config files placed outside git or committed only as building placeholders, store accounts/signing.
- **Android:** dev application-id suffix; crash-reporter plugin in the convention plugin; push service registered + token refresh handled; deep links/App Links filters per host; debug-only broadcast receiver to trigger push/overlay flows without the vendor; overlay permission via `appops` on the emulator; release build smoke test after any keep-rule change.
- **iOS:** 4 configurations wired xcconfig → plist → `AppEnvironment`; placeholder plist must not crash (guard the vendor init); simulator ad-hoc signing (`CODE_SIGN_IDENTITY=-`, never `CODE_SIGNING_ALLOWED=NO`); push tested with `xcrun simctl push booted <bundle> sample.apns`; time-sensitive/critical notification entitlements listed as owner inputs; SPM product additions with all four pbxproj entries.
- **Both:** vendors behind core ports with fakes (push token, crash, analytics, app-instance id, maps, OTP delivery); events arriving by socket and push de-duplicated by entity id; refresh on foreground; one-time code length/timer from backend config; verify call sent as a public request (no refresh-retry on 401).
- **Proof:** a table in the task block: integration × platform × (unit test | emulator/simulator | real device | blocked on owner).

## 8. Performance pass with the Android skills
1. Measure first, on a release + minified build, on a quiet machine or a real device; record the baseline numbers (startup, frame drops per journey, APK size, heap) — debug builds and busy hosts give misleading numbers.
2. `jetpack-compose-performance`: scan the slow screens for unstable parameters, missing lazy `key`/`contentType`, state read in the draw phase, `derivedStateOf` candidates; fix, re-measure.
3. `android-profiler`: record a Perfetto trace of the journey (startup, scroll, the heaviest screen); analyze jank, binder stalls, memory/LMK; A/B against the baseline trace.
4. `anr-audit-and-fix`: static scan of main-thread blocking after adding platform bridges, receivers or overlays; triage any ANR trace from QA.
5. `r8-analyzer`: review keep rules for broad package-wide rules and redundancies; keep a release APK size budget in the gate; smoke-test the release build on a device after every keep-rule change.
6. Report before/after per metric with the measurement conditions; unmeasured "optimizations" are not gains. Skills' scripts are local-only analysis (read each `SKILL.md` before use; license file sits beside them).

## 9. Adding a contract field (server → clients)
1. Server task: change the validation schema (source of the OpenAPI), service and tests; additive within a phase (optional field, new enum value documented in `BUSINESS_DOMAIN.md` §2/§11 with AR+EN messages for new codes).
2. Regenerate the docs (`npm run docs` or equivalent) and commit the generated OpenAPI/Postman; the contract fingerprint test fails until the change is recorded with its client-impact note.
3. In the server task block: "Contract: <operation ids>; affected tasks: ADM-xxx, APP-xxx"; add those client rows (BLOCKED on the server task) if they do not exist.
4. Merge the server PR; `tasks.py set <SRV-ID> DONE` flips the client rows to TODO.
5. Each client: `apiSync`/`api:sync` on a task branch from its master, regenerated code committed, fixtures/mock transport updated (new field present with value hints), enum/label tests updated, UI uses the field; gate's contract-drift check green.
6. Admin/app tasks name the server task in their block; the server's `Integration.md` and the client's `Integration.md` list the new operation/field.

## 10. Adding a project to the workspace
1. Folder `<Name>/` with `CLAUDE.md` (from `docs/templates/PROJECT_CLAUDE_TEMPLATE.md`: stack, gate command, layers), `.claude/{session,memory,Integration}.md` (templates in `docs/templates/`), `docs/<Name>_PRD.md`, `docs/<Name>_BRD.md`, `docs/<Name>_Tasks.md` (TASKS_TEMPLATE: Stage A scaffold rows, rows needing other projects start BLOCKED).
2. One entry in `.claude/projects.json`: key, `title`, `prefix` (unique, upper-case), `dir`, `master` (an existing master, e.g. SDKs ship with `server`, or a new one), `backlog`, `session`, `memory`, `integration`.
3. New master? `git branch --no-track <master> origin/main && git push origin <master>` from the Terminal panel; protect it like the others; add it everywhere the masters are listed: rules §3.2, memory, `INTEGRATION.md` §1.
4. `INTEGRATION.md` §1 row (role, master, backlog), §3 edges it adds, §6 readiness; root `.claude/session.md` index row; root `CLAUDE.md` §2 map row.
5. `python3 scripts/tasks.py check` OK, `python3 .claude/hooks/test_hooks.py` green (masters and session files are read from the registry — no hook edit needed), `tasks.py board`.
6. Commit on a `docs/` or `chore/` branch into the owning master; the first `tasks.py next <key>` must return its scaffold row.
