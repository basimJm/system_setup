## 1. Executive Summary
One package that proves a user controls a phone number: it issues a short code, delivers it through a replaceable channel, verifies it under abuse limits and returns a single-use token the backend spends on login, registration or a sensitive action.

## 2. Business Context
Phone verification is on the critical path of sign-up and sign-in. Vendors change (WhatsApp, SMS providers), limits must stop abuse without locking out honest users, and the backend must never trust a code twice.

## 3. Goals
- G1 Request → verify → consume with one stable interface.
- G2 Abuse limits: resend cooldown, requests per window, wrong-code limit, temporary block, admin unblock.
- G3 Single-use proof (`otpToken`) with its own expiry.
- G4 Works on a laptop without a vendor; strict in production.

## 4. Scope
### 4.1 In Scope
Code generation and hashing, delivery through a channel port, verification outcomes, limits and blocks, token issue and consumption, memory store and fake channel.
### 4.2 Out of Scope
Vendor contracts and message templates (channel adapters), session/JWT issuance, user records, UI copy.

## 5. Business Requirements
| ID | Requirement | Acceptance |
|---|---|---|
| OTP-R1 | A code is numeric, has a configured length and expires | `codeLength`, `codeTtlSec`; `EXPIRED` afterwards |
| OTP-R2 | A user cannot request again before the cooldown | `RATE_LIMITED { retryAfterSeconds }` |
| OTP-R3 | Too many requests or wrong codes block the phone for a while | `BLOCKED { retryAfterSeconds }`; admin `resetLimits` |
| OTP-R4 | A correct code can be used once, even under concurrent requests | exactly one `VERIFIED` |
| OTP-R5 | The proof of verification is spent once and matches phone + purpose | `consumeToken` → `valid` once, then `UNKNOWN_TOKEN` / `MISMATCH` |
| OTP-R6 | Codes are never stored in clear nor logged | HMAC hashes; masked phones in logs |
| OTP-R7 | A failed delivery does not consume the cooldown | code removed, cooldown lifted, typed error |

## 6. Non-Functional Requirements
Stable error codes; atomic store operations in production; constant-time comparison; ≥ 95 % coverage; ESM + CJS.

## 7. Success Metrics
No double use of a code or token; vendor switch = one adapter + configuration; `npm run verify` green.

## 8. Risks & Mitigations
| Risk | Mitigation |
|---|---|
| Brute force | wrong-code limit + block, short TTL |
| SMS pumping / cost abuse | request window + block; consumer adds per-IP limits |
| Vendor outage | typed `DELIVERY_FAILED`, retryable; alternate channel by configuration |
