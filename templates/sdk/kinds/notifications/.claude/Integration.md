## 1. Purpose and boundaries
Send push notifications (device tokens) and emails through one facade with validation, idempotency, token chunking, retries of transient failures and a per-token report that tells the consumer which tokens to delete.

**Not in this package:** templates and copy (consumer), who gets notified (consumer), vendor SDKs (one adapter per vendor behind `PushSender` / `EmailSender`).

## 2. Architecture
```
consumer ──> createNotifications(options) ──> Notifier (port) = NotifierService
                                              ├── PushSender   port: FakePushSender | vendor adapter (FCM, APNs…)
                                              ├── EmailSender  port: FakeEmailSender | vendor adapter (SMTP, API…)
                                              └── IdempotencyStore: memory (local) | consumer's Redis (shared)
kernel (src/kernel.ts): errors · zod options + prod rules · redacting logger · retry/backoff · timeout
```

## 3. Public API (port)
```ts
interface Notifier {
  sendPush(message: { tokens; title?; body?; data?; priority?; collapseKey? }, options?: { idempotencyKey? }): Promise<{
    results: { token; status: 'SENT'|'INVALID_TOKEN'|'FAILED'; errorCode? }[];
    invalidTokens: string[]; sent: number; failed: number; duplicate: boolean }>;
  sendEmail(message: { to; subject; text; html?; replyTo?; tags? }, options?): Promise<{ id; status: 'SENT'|'QUEUED'; duplicate }>;
  close(): Promise<void>;
}
createNotifications(options): Notifications   // Notifier + { pushSender, emailSender }
```
Vendor ports: `PushSender.send(message) → TokenResult[]` (per token `SENT | INVALID_TOKEN | RETRYABLE | FAILED`; throw only for whole-call failures), `EmailSender.send(message) → { id, status }`, `IdempotencyStore.claim(key, ttlMs) → boolean`.

## 5. Status and result mapping
| Vendor answer | Normalized |
|---|---|
| token delivered | `SENT` |
| token unregistered / malformed | `INVALID_TOKEN` → listed in `invalidTokens` (consumer deletes it) |
| token transient (unavailable, quota) | `RETRYABLE` → re-sent with backoff; after `retry.maxAttempts` → `FAILED` |
| token missing from the vendor answer | `FAILED` |
| whole call throws | retried; then `PUSH_FAILED` / `EMAIL_FAILED` (an `SdkError` from the adapter is kept) |
| call exceeds `timeoutMs` | `TIMEOUT` (retryable) |
| idempotency key seen within TTL | nothing sent, `duplicate: true` |

## 6. Error model
`SdkError { code, message, retryable, cause, details }`. Codes: kernel + `__SDK_PREFIX___PUSH_FAILED`, `__SDK_PREFIX___EMAIL_FAILED`, `__SDK_PREFIX___DUPLICATE` (reserved). Logs use `reason` for codes (the redacting logger masks any field named `*code`).

## 7. Environments
Dev: `provider: 'fake'` channels (what was sent is on `notifier.pushSender.sent` / `emailSender.sent`). Prod: `custom` channels with real adapters, shared idempotency store.

## 8. Performance notes
Tokens are de-duplicated and chunked; only `RETRYABLE` tokens are re-sent; one timeout per vendor call; no global state.

## 9. Testing
`npm test` (coverage gate), `npm run test:loop` = 300 push + email flows × 25 concurrent with invalid, retryable and whole-call failures plus duplicate keys, every token delivered once; `npm run test:smoke-package` through CJS and ESM.

## 10. Adoption guide (any project)
1. Write one `PushSender` and/or `EmailSender` adapter per vendor (map every vendor code to a `TokenStatus`).
2. `createNotifications({ environment, push: { provider: 'custom' }, pushSender, email: {...}, emailSender, idempotencyStore })` once.
3. Use `idempotencyKey` = business event id (e.g. `booking:<id>:approved`) so job retries never double-send; delete `invalidTokens` from the device table.
4. Tests: `provider: 'fake'`.

## 11. Open questions / assumed-missing requirements
- No vendor adapters yet (`NOT-002`, `NOT-003`).
- Templating / localisation stays with the consumer unless the owner wants it here (`NOT-004`).
- Per-user rate limits and quiet hours are consumer policy.
