## 1. Executive Summary
One package through which __SYSTEM_NAME__ collects online payments by hosted checkout, verifies them server-side, refunds them and authenticates gateway webhooks, with the gateway vendor replaceable by configuration.

## 2. Business Context
Online payment is a conversion and trust point: the backend must never fulfil on an unverified redirect, must refund automatically where policy says so, and must survive gateway outages and duplicate callbacks. Phase 1: the platform collects; Phase 2: split payments to sub-merchants (design kept open).

## 3. Goals
- G1 Create → verify → refund → webhook behind one port.
- G2 Idempotent create and refund (job retries are safe).
- G3 Authenticated, replay-safe webhooks.
- G4 Full local development without a vendor (mock gateway).

## 4. Scope
### 4.1 In Scope
Checkout sessions, verification, full/partial refunds, webhook parsing, fake gateway, localhost mock gateway with its generic adapter, Phase-2 `destinations` pass-through.
### 4.2 Out of Scope
Card data handling, pricing and deposit rules, payouts and settlement reports, vendor-specific flows (adapters), invoices.

## 5. Business Requirements
| ID | Requirement | Acceptance |
|---|---|---|
| PAY-R1 | Amounts are integer minor units in an enabled currency | validation; `currencies` option |
| PAY-R2 | The same checkout attempt never creates two sessions | `idempotencyKey` → same session; different body → `IDEMPOTENCY_CONFLICT` |
| PAY-R3 | Fulfilment relies on server-side verification only | `verify` is the truth; redirect params are ignored by the port |
| PAY-R4 | Webhooks are authenticated and fresh | HMAC + timestamp tolerance; `AUTH_FAILED` / `WEBHOOK_INVALID` |
| PAY-R5 | Refunds are idempotent and never exceed the paid amount | `REFUND_NOT_ALLOWED` |
| PAY-R6 | Unknown gateway statuses are never treated as paid | `UNKNOWN` + warning |
| PAY-R7 | Production refuses the fake gateway, plain http and weak secrets | `CONFIG_INVALID` |

## 6. Non-Functional Requirements
Typed errors with stable codes; retries only on transient failures; timeouts; no secrets logged; ≥ 95 % coverage; ESM + CJS.

## 7. Success Metrics
Zero fulfilments without `PAID`; zero duplicate charges from retries; vendor switch without consumer code changes.

## 8. Risks & Mitigations
| Risk | Mitigation |
|---|---|
| Gateway outage during checkout | typed `UNAVAILABLE`, consumer keeps the order pending and re-verifies |
| Replayed or forged webhooks | signature + tolerance + `eventId` de-duplication by the consumer |
| Vendor status vocabulary drift | strict enum mapping with `UNKNOWN` |
