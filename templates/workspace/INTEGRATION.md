## 2. Contracts (the wire format every client builds against)
- **REST:** generated from server code into `__SERVER_DIR__/docs/api/openapi.<namespace>.json` (+ Postman collection and environment) by the server's docs command on every endpoint change; committed with the server task. There is no hand-written contract folder.
- **Clients regenerate, never hand-write DTOs:** admin `npm run api:sync`; apps their `apiSync` Gradle task; both fail their gate when the generated code drifts from the committed contract.
- **Envelope:** `{success,message,data,meta?}` / `{success:false,message,error:{code,details?,traceId}}`. Clients branch on `code` only. Error codes are listed in `BUSINESS_DOMAIN.md` §11 and both locales of every client (tests enforce parity).
- **Compatibility:** contract changes are additive within a phase; a breaking change gets a new task in every consuming project (named in the server task block) and the clients' rows are BLOCKED on it until merged.
- **Known shapes that bit clients before:** optional objects omitted instead of empty (`data`/`params` missing), id patterns no real id matches, idempotency headers missing from one namespace's spec — check the generated spec against a real response before shipping a client.

| Server → third parties (push, email, object storage, gateway) | provider docs | fake providers; production rejects `fake` | _…_ |

**Working without the other side (mandatory):** a client builds against the committed contract with mock fixtures and marks any missing endpoint as a BLOCKED row on a server task; the server builds behind fake providers until the owner supplies keys. Nothing is built on an invented endpoint.

## 4. Auth
- Clients: one-time code requested from the server, delivered through the OTP provider port (dev/QA `OTP_PROVIDER=fake` + fixed code; production refuses `fake`), verified into a single-use proof token that login/register/sensitive actions consume; JWT access (scope = namespace) + rotating refresh (reuse revokes the family).
- Staff/admin: email + password + second factor; lockout after N failures (settings).
- Permissions: a fixed list of grantable keys enforced on every endpoint, socket event and notification; UI hides what the token lacks.

## 5. Real-time, push, jobs, storage, analytics
- Real-time: socket rooms per user / per tenant (permission-filtered) / admin; every live event has a push data message twin and a refresh-on-foreground fallback, de-duplicated by entity id.
- Push: one project per environment, one registration per app × platform (owner input). Email through SMTP from a configured sender (keys in env only).
- Jobs: queue + cron with deterministic job ids (reminders, pending alerts, auto-cancel/expiry, subscription checks, grace deletion, reports).
- Storage: presigned upload → device compression → direct upload → confirm → CDN URL; private files via signed URLs; local object-storage emulator on dev (`http` links need a dev-only allowance in web clients).
- Analytics: apps track screens/actions client-side (Firebase or equivalent); server events in the database; apps never send analytics to the backend.

## 6. Environments and definition of "integration ready"
- `dev` and `prod` for every part; dev builds point at the hosted dev API once the owner deploys it, until then at a local stack (`PLAYBOOKS`: local QA stack). Production builds compile the mock data source out.
- A part is integration-ready when: its gate is green, its contract (server) or regenerated DTOs (clients) are committed, its fake/mock paths are documented here, and its owner inputs are listed as PENDING rows.
- Release order: server (+ SDKs) → admin → apps.
